# Verification

vynamp-decode does not trust a decoder until it has been checked against something
independent of itself.

## Synthetic round trips

`vynamp-decode-testkit` writes containers (WAV, RF64, BW64, Wave64, AIFF, AIFF-C) from
known samples. Tests decode them back and require bit-exact equality. These
prove the demuxers and the PCM decoder against the specifications.

## Third-party oracle corpus

`tests/fixtures/pcm/` holds files written by FFmpeg from
`tools/fixtures/source-sine.wav` (a deterministic 24-bit-precision sine, itself
generated by `vynamp-decode-testkit`). `MANIFEST.txt` records, per file:
`arquivo|sha256|rate|channels|spec|frames|gerador`, where the last column is the
generator's version line. `crates/vynamp-decode/tests/oracle_pcm.rs` checks each file's
SHA-256 and requires the decoded samples to equal the source converted with
FFmpeg's rule (integer narrowing truncates; float is `x / 2^31`).

FFmpeg is a development tool only. It is never a dependency and never runs in
the test suite; regenerate the corpus with `tools/fixtures/generate.ps1`.
PCM fixtures stay below 2 MiB in total.

## FLAC oracle corpus

`tests/fixtures/flac/` holds FLAC files written by FFmpeg from the same source: 16, 24 and
32-bit (the latter needs `-strict experimental`), mono, stereo and 6 channels, 44.1, 48, 96 and
192 kHz, compression levels 0, 5, 8 and 12, fixed, Levinson and Cholesky prediction, frame sizes
192, 4096 and 16384, forced left/right/mid-side stereo, a Vorbis comment block and a stream
with wasted bits (16-bit content in a 24-bit stream). FLAC is lossless, so the oracle is the
PCM the encoder received: `generate.ps1` writes it with the same filter chain as a WAV in
`ref/`, checks that FFmpeg's own decoder returns it, and `oracle_flac.rs` requires our decoder
(Strict, STREAMINFO MD5 verified) to match it sample for sample. The pinned FFmpeg cannot
write 8-bit FLAC (the encoder takes s16 and s32 only) nor SEEKTABLE or ID3v2 blocks; those are
covered by hand-assembled streams and by a test that prefixes an ID3v2 tag.

## FLAC conformance corpus

The IETF CELLAR `flac-test-files` are CC0 and part of them is committed unmodified in
`tests/fixtures/flac-conformance/` (about 7.8 MiB: 20 of the 67 `subset` files, covering 8, 12,
20 and 24 bit, 1 to 8 channels, wasted bits, escape partitions, all fixed orders, 22.05 kHz,
the legacy variable block size layout and predictor-overflow signals, plus 11 `faulty` files).
`conformance_flac.rs` requires every `subset` file to decode to the end in Strict mode (the
decoder fails on a STREAMINFO MD5 mismatch) and every `faulty` file to fail in Strict mode
without panicking; file 10 (invalid Vorbis comment) is excluded until comments are parsed in
plan 04.

To run the complete groups (all 67 `subset` files, including the very large metadata ones,
and all `faulty` files), clone the repository and point the test at it:

```text
git clone --depth 1 https://github.com/ietf-wg-cellar/flac-test-files <dir>
VYNAMP_FLAC_TEST_FILES=<dir> cargo test -p vynamp-decode --release --test conformance_flac
```

With the default limits all 67 files pass. Because FLAC passes its official vectors, its
container and codec are `conformance` in the support matrix.

## Malformed-input smoke tests

Each demuxer and decoder is exercised with truncated, oversized and
self-contradictory inputs. They must return an `Error`, never panic, and never
allocate beyond the configured limits (an allocation-counting allocator in the
testkit checks that steady-state decoding does not allocate).

## Future: fuzzing

Fuzzing needs tooling outside the std-only rule, so it will live in a separate,
unpublished harness. Until then the smoke tests above are the only line of
defence against hostile input.
